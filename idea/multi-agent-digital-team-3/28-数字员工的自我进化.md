## 本节摘要

如果一个团队运行一年，第一天和第三百六十五天的工作质量完全一样——它没有在成长。对人类团队来说，这是危险信号；对数字团队来说，这是设计缺陷。

今天是模块四的最后一课。核心不是日志怎么写、不是提案怎么落地，而是怎么做复盘——怎么从一堆运行数据里找到"到底该改哪一行"。

---

## 一、认知原点：自我进化是什么？

数字团队的自我进化，本质就是人类团队复盘文化的工程化版本。五步闭环：

1. **记录**：用结构化日志取代人类的记忆
2. **复盘**：Agent 定期回看执行记录，定位失败根因
3. **提案**：把改进方案写成结构化文档，附带具体证据
4. **落地**：经人类审批后，机械地更新 soul / SOP / Skill 文件
5. **验证**：检查改进后指标是否真的上升

> **最难的是复盘。** 记录和落地都是工程基础设施，看代码就懂。但"怎么从上千条日志里找到'到底该改哪一行'"——这是方法论问题。

---

## 二、为什么需要自我进化

没有自我进化机制时，三件事必然发生：

1. **同样的错误反复出现** — PM Agent 每次忘了检查移动端适配，人类反馈从没被写进 SOP，等上下文窗口一刷新就永远消失了
2. **工具调用路径越来越冗余但没人知道** — API 接好了但 Skill 没更新，效率损耗永远不会被发现
3. **协作设计问题被误归因给个体** — 实际上是 PM 和 Dev 之间的交接文档格式不清晰，却被当成某个人的问题

真正的解法：让系统自己把"值得关注的信号"提炼出来，再交给人类决策。

## 三、三层日志：复盘的原料

> 建立在 25（session 日志）、26（共享工作区 + 三态邮箱）、27（human.json 介入通道）的基础上。

| 层级 | 记录什么 | 核心用途 | 写入方式 | 保留策略 |
|------|---------|---------|---------|---------|
| L1 人类交互层 | 每次人类纠正 | 黄金数据——Agent 判断偏差的最直接信号 | `send_mail(to=human)` 内自动追加 | 永久保留 |
| L2 任务-Agent 层 | 每个任务一条摘要（含质量分） | 定位"哪些任务做得差" | task_callback hook 自动写 | 保留 90 天 |
| L3 ReAct 循环层 | Agent 内部每步推理 | 定位"差在哪一步" | 复用第 25 课 session 日志 | 滚动 30 天 |

**三层里最值钱的是 L1**——每一次人类纠正都是黄金数据。Agent 自己觉得做得挺好，但人类说"不对，移动端方案呢"——这条纠正比 Agent 自己的 10 条分析都有价值。

**为什么不合并成一层？** 三层的生命周期完全不同：L1 稀缺宝贵永久保留，L3 量最大 3 个月前的推理步骤对今天毫无用处。合并会导致保留策略冲突。

**L1 写入是 AOP 落地**：在 `send_mail()` 里加一行判断，凡是发给 `to="human"` 的消息就自动追加 L1 日志，调用方零感知。

```python
# tools/mailbox_ops.py（第 28 课对第 27 课唯一的改动）
def send_mail(mailbox_dir, to, from_, type_, subject, content) -> str:
    # ... 原有写入逻辑不变 ...
    # 💡 to=human 时自动写 L1 日志，调用方零感知
    if to == "human":
        _write_l1_log(mailbox_dir, message)
    return msg_id
```

**L3 不需要另建**：复用第 25 课 session 日志，只加 `task_id` 索引（`sessions/index.jsonl`）让复盘能按任务切片回放。

## 四、复盘方法论：从"出了问题"到"改哪一行"

### 4.1 复盘失败的两个层次

- **第一层**：只知道"出了问题"——"PM 的质量分偏低"，然后就没有然后了
- **第二层**：复述式反思——"下次生成设计文档时要注意移动端适配"，听起来像根因分析，其实只是把失败过程重新描述了一遍

> Reflexion 论文（NeurIPS 2023）：犯错的 Agent 在评估自己的错误时，倾向于合理化而不是纠正。Retroformer（ICLR 2024）进一步发现：自由文本反思会系统性地产生"复述式反思"，需要结构化约束来打破这个循环。

### 4.2 有效复盘的五个递进问题（漏斗模型）

| 问题 | 数据源 | 输出 |
|------|-------|------|
| ① 哪些任务做得差？ | L2 定量 | 最差的 N 条任务 |
| ② 差在哪一步？ | L3 下钻 | 具体失败的 ReAct 步骤 |
| ③ 人类怎么看？ | L1 交叉验证 | 人类纠正记录 |
| ④ 根因是什么类型？ | 枚举分类 | 4 种根因之一 |
| ⑤ 改哪个文件的哪一段？ | 精确改动 | before/after_text 锚点替换 |

**大多数复盘死在第 ④ 步**——知道"出了问题"，但不知道"根因是什么类型"。

**解法**：逼 Agent 从枚举中选 `root_cause`：

| 枚举值 | 含义 | 改动对象 |
|-------|------|---------|
| `sop_gap` | 流程缺步骤 | agent.md / skills/*.md |
| `prompt_ambiguity` | 指令模糊 | soul.md |
| `ability_gap` | 经验不足 | memory.md |
| `integration_issue` | 协作问题 | agent.md 协作部分 |

设计方法叫**以终为始**：先想清楚"我最终能改什么"，再反推根因分类。Agent 一旦完成归因，就立刻知道要改哪个文件——路径确定，不需要再做一轮推理。

## 五、自我复盘实战（PM Agent 走一遍完整分析链）

### 5.1 核心架构

```
┌──────────────────────────────────────────────────────┐
│  self_retrospective/SKILL.md（思考框架）               │
│  - 五个递进问题（非强制顺序）                          │
│  - root_cause 枚举约束                                │
│  - 输出格式要求（RetroOutput JSON）                   │
└──────────────────────┬───────────────────────────────┘
                       │ Agent 按需调用
                       ▼
┌──────────────────────────────────────────────────────┐
│  tools/log_query.py（统一 CLI，纯数据查询）            │
│  stats / tasks / steps / l1 / all-agents             │
└──────────────────────┬───────────────────────────────┘
                       │ Agent 推理分析
                       ▼
┌──────────────────────────────────────────────────────┐
│  RetroOutput JSON（结构化产出）                        │
│  - retrospective_report: 发现 + 证据                 │
│  - improvement_proposals: root_cause + before/after  │
└──────────────────────────────────────────────────────┘
```

**Skill vs Script 的本质区别**：Script 规定动作序列，Skill 提供思考框架。SKILL.md 只告诉 Agent "要思考什么"，不规定"先查什么再查什么"。

### 5.2 场景：PM 过去一周运行了 8 个任务（模拟推理过程）

**Agent 思考 ①：先看整体统计**
```bash
python3 tools/log_query.py stats --agent-id pm --days 7
# → {"task_count": 8, "avg_quality": 0.68, "failure_count": 3, "human_correction_count": 3}
```
有问题——需要下钻。

**Agent 思考 ②：哪些任务做得差？**
```bash
python3 tools/log_query.py tasks --agent-id pm --days 7 --sort quality_asc --limit 3
# → 三条最差的全是设计文档类任务。模式出现了。
```

**Agent 思考 ③：差在哪一步？**
```bash
python3 tools/log_query.py steps --task-id t001 --agent-id pm
# → 只有 3 步：读需求 → 生成文档 → 提交
# "检查移动端适配"从来没出现在 Agent 的执行路径里
```

**Agent 思考 ④：人类怎么看？**
```bash
python3 tools/log_query.py l1 --days 7 --keyword "移动端"
# → 2 条退回记录，全指向：缺移动端适配
# L1（人类纠正）验证了 L2/L3 的发现
```

**Agent 思考 ⑤：分类根因**

自由文本会写："下次生成设计文档时要注意移动端适配"——复述失败，不是根因。

枚举约束逼出真正分类：这是 `sop_gap`——`product_design` Skill 里根本没有"检查移动端"这一步。

### 5.3 最终产出：RetroOutput JSON

```json
{
  "retrospective_report": {
    "agent_id": "pm",
    "period": "2026-04-14 ~ 2026-04-20",
    "summary": "设计文档任务质量偏低，根因是 product_design Skill 缺少移动端检查步骤",
    "findings": [{
      "pattern": "3/8 任务被退回，全是设计文档类，退回原因均为缺少移动端适配",
      "evidence_task_ids": ["t001", "t003", "t006"]
    }]
  },
  "improvement_proposals": [{
    "root_cause": "sop_gap",
    "target_file": "skills/product_design/SKILL.md",
    "before_text": "1. **需求来源**：从 `/mnt/shared/needs/requirements.md` 读取原始需求",
    "after_text": "1. **需求来源**：从 `/mnt/shared/needs/requirements.md` 读取原始需求\n2. **多端检查**：如需求涉及用户界面，必须明确桌面端/移动端差异并分别设计",
    "expected_improvement": "设计文档 checkpoint 通过率从 62% 提升至 85%+",
    "evidence": ["t001", "t003", "t006"]
  }]
}
```

**三个关键约束：**
- `evidence` 不允许空——人类审批时应点开日志 ID 查原始记录，而不是盲信 Agent 分析
- 一次最多 3 条提案——超过 3 条说明 Agent 在发散而不是聚焦
- `before_text` 不允许空——逼 Agent 读文件、找到精确位置

## 六、团队复盘：自我复盘看不到的视野

自我复盘精度高（能下钻到具体哪个 ReAct 步骤失败），但视野窄（只看自己的日志）。

**团队复盘由 Manager 执行**，看 L1 全量 + 所有 Agent 的 L2 聚合，能发现：
- **跨 Agent 的模式**：也许不只 PM 有移动端问题，也许是 SOP 模板本身缺了这一步
- **协作设计问题**：PM 和 Dev 之间交接失败率最高，不是某个人的问题
- **瓶颈识别**：PM 平均质量 0.68，Manager 平均 0.88——PM 是瓶颈

**级联触发**：Manager 发现瓶颈 Agent 后，不做 L3 级深分析（那是 Agent 自己擅长的），而是发 `retro_trigger` 邮件给 PM，让 PM 启动自我复盘。**各做各擅长的**：自我复盘 = 精度，团队复盘 = 视野。

团队复盘还有重要产出：**周报发给人类**——不只发改进提案等审批，也发完整团队运行状况。人类对数字团队的信任，来自"系统能主动告诉我它在哪里有问题、在怎么改"。

## 七、三档 HITL 审批：改动越深，审批越重

**为什么不能让 Agent 自己落地？** soul 一旦改错，Agent 所有后续判断都会跟着偏——包括它下一次复盘对自己的评价。这是无法自我纠正的漂移（Goal Drift, 2025）。

| 档位 | 改动对象 | HITL 方式 | 示例 |
|-----|---------|---------|------|
| 档 1 | memory | 自动落地 + 硬闸门（3 条/天，200 行上限） | memory.md 加一条经验 |
| 档 2 | skill / SOP | Manager LLM 预审 + Human 批准 | product_design 加移动端检查步骤 |
| 档 3 | soul / code | Human 必审 + 强制 Dry Run | 调整 PM 风格偏好、修改代码逻辑 |

**审批走邮箱闭环路由**：PM → Manager → Human → Manager → PM。延续第 27 课的单一接口原则——Human 只有一个对接人（Manager）。

## 八、代码实践框架：旁路系统，只加文件不改架构

```
m4l28/
├── tools/
│   ├── mailbox_ops.py          # ⚡ L1 一行改动（to=human 时自动写 L1）
│   ├── log_ops.py              # 三层日志读写 Python 库
│   └── log_query.py            # ⚡ 统一日志查询 CLI
├── schemas.py                  # RetroOutput + ImprovementProposal
├── tools/proposal_ops.py       # 提案分档 + 闸门校验
├── scheduler.py                # 双条件触发（24h 间隔 + ≥5 条任务）
├── seed_logs.py                # 演示数据生成 + 工作区 baseline 重置
├── workspace/pm/skills/
│   └── self_retrospective/SKILL.md   # ⚡ 纯思考框架
└── workspace/manager/skills/
    ├── team_retrospective/SKILL.md
    └── review_proposal/SKILL.md
```

**端到端数据流：**
```
seed_logs.py（生成 7 天模拟数据）
    ↓
Scheduler.tick()（24h + ≥5 条任务 → 发 retro_trigger 邮件）
    ↓
PM 加载 self_retrospective Skill → 调用 log_query CLI → LLM 推理
    ↓
PM 产出 RetroOutput JSON → 发 retro_report 邮件给 Manager
    ↓
Manager 加载 review_proposal Skill → 按 target_file 分档
    ↓
Manager 转 Human 审批 → 发 retro_approved/rejected 给 PM
    ↓
PM 收到 approved → 机械执行 before_text → after_text 替换
    ↓
PM 发 retro_applied 确认邮件 → 闭环完成
```

**分工原则**：LLM 负责看和想，机械操作负责做。文件替换是纯字符串匹配——找到 `before_text`，替换为 `after_text`。找不到就报错，不硬改，不猜测。

## 九、深入框架：为什么这样分层

### 9.1 学术根基

本课是 **Reflexion 模式（NeurIPS 2023）的异步批次版本**：不更新模型权重，而是通过结构化反思生成"经验"，写回 soul/SOP 文件。

针对 Reflexion 的局限（Agent 倾向于合理化自己的错误），设立三道防线：
1. `root_cause` 枚举约束——打破复述式反思
2. L1 交叉验证——用人类纠正信号覆盖 Agent 自评偏差
3. `evidence` 强制非空——让人类审批时可绕过 Agent 分析直接看原始数据

> **核心原则**：Agent 负责发现改进点，Human 负责决定要不要改。打破这条线，系统就从工程坍缩成赌博。

### 9.2 为什么 Skill 不规定调用顺序

- 场景不同，路径不同：全部任务质量高，第 ① 步就结束；L1 纠正记录多，先看 L1 更高效
- Agent 的判断力是资产：SKILL.md 提供思考框架，不是操作手册
- 工具层只做数据查询：`log_query.py` 不帮你排序选 top-k，判断留给 Agent

### 9.3 工程分层

| 任务 | 谁做 | 为什么 |
|------|------|-------|
| 看日志、发现模式、分类根因 | LLM（Agent 推理） | LLM 擅长语义理解和判断 |
| 提供数据 | log_query.py CLI | 纯查询，输出 JSON，不做判断 |
| 写出 before/after_text | LLM（Agent 产出） | 读文件内容，写出锚点 + 替换文本 |
| 审批 | Human（或 Manager LLM 预审） | 防止自我纠正失效 |
| 机械执行文本替换 | PM Agent（收到 approved 后） | 纯字符串匹配替换，找不到就报错 |

> 和 Cursor/Claude Code 的相似性：LLM 产出"改什么"的意图（before/after_text），执行侧做精确 apply。LLM 不需要手写 unified diff、不需要算 SHA256，只做自己擅长的事。

## 十、避坑指南

### 🚫 严重破坏稳定性的反模式

| 反模式 | 危害 | 解法 |
|-------|------|------|
| 复述式反思代替根因分析 | LLM 几乎总会写出"下次要注意 X" | root_cause 必须从枚举中选 |
| Agent 自动落地 soul/SOP 改进 | soul 改错后所有判断都会偏，无法自我纠正 | 自动落地只用于档 1（memory），且加硬闸门 |
| 样本不足强行复盘 | 基于 2-3 条任务推断噪声极大，可能优化掉本来正确的行为 | 设定 min_tasks=5，不足直接跳过 |
| 自动审查误报侵蚀信任 | 误报率高（约 12.5%），团队逐渐停止审查，审批形同虚设 | 控制提案数量和质量比控制审批流程更重要 |
| 补丁累积导致文件膨胀 | 模型倾向"加规则"而不是"改规则"，半年后 SKILL.md 从 20 行膨胀到 200 行充满矛盾约束 | 定期"小重构"：合并重复规则、删除过时补丁 |

### 💡 稳健落地的最佳实践

| 最佳实践 | 要点 |
|---------|------|
| 提案必须附 Evidence | 至少 1 条日志 ID，审批时点开日志查原始记录而不是信任 Agent 摘要 |
| 基于上下文匹配而非行号 | before_text / after_text 锚点替换（GPT-4.1 官方也推荐避免行号） |
| 思考框架引导而非脚本管线 | Skill 给约束和问题，不规定顺序（Flow-of-Action, ACM 2025） |
| 设置最大迭代限制 + 优雅退出 | 默认限制 3 轮反思，连续 2 次无改进则停止，防止无限循环 |
| 变更历史分条保留支持单条回退 | 每条提案独立存储 before/after，发现问题只回退那一条（同 git commit 粒度原则） |

## 总结

- **自我进化 = 五步闭环**：记录 → 复盘 → 提案 → 落地 → 验证
- **三层日志**：L1（人类纠正，黄金数据，永久保留）、L2（任务摘要，定位瓶颈）、L3（复用第 25 课 session 日志 + task_id 索引）
- **复盘架构**：Skill = 思考框架，CLI = 数据查询，Agent = 推理分析
- **漏斗模型**：五个递进问题从上千条日志收窄到精确文件锚点替换
- **三档 HITL**：memory 自动 + 闸门 / skill/SOP Manager 预审 + Human 批准 / soul/code Human 必审 + Dry Run

**模块四收官**：角色设计（25）→ 任务流转（26）→ 人类介入（27）→ 自我进化（28）
