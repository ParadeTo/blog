## 这一讲的核心问题

这节课讨论的是：当 Agent 从“生成回答”变成“调用工具执行动作”以后，安全问题的重心会发生变化。

传统 Chatbot 的风险主要落在输出层：模型可能被诱导说错话、泄露信息、给出危险建议。Agent 的风险更靠近执行层：一旦它能调用 Shell、文件系统、邮件、HTTP 请求、数据库、内部系统，错误决策就可能变成真实副作用。

所以这一讲的关键判断是：

- Agent 安全不是只管模型怎么想，而是要管工具能不能被调用、以什么参数调用、在什么身份和环境里调用。
- Prompt 只能表达意图，不能构成强制边界。
- 真正可靠的边界要落到 Hook、权限网关、沙箱、身份认证、审计这些确定性机制上。

## 课程逻辑

### 1. 先区分 Agent 安全和 Chatbot 安全

课程先把认知起点放在“Agent 不只是聊天”上。

Chatbot 被 prompt injection 攻击时，常见结果是回答偏离、幻觉、泄露上下文。Agent 被攻击时，风险会穿过模型输出，进入工具调用链路。例如：

- 读写本地文件
- 执行命令
- 发起网络请求
- 调用邮件、日历、工单、内部 API
- 读取或携带凭据
- 安装或运行不可信依赖

这意味着安全边界不能只放在模型前后，也不能只靠“告诉模型不要做坏事”。Agent 系统必须在工具调用之前有一层独立检查。

### 2. Prompt 为什么管不住安全

课程用实验和工程现象说明：即使系统提示词写得很完整，模型仍然可能在复杂上下文里忽略它。

这里的重点不是“模型不听话”，而是 prompt 的性质决定了它不能充当安全边界：

- Prompt 是自然语言约束，不是强制执行机制。
- Prompt 和用户输入、网页内容、文件内容、工具返回值都混在同一个上下文里。
- 攻击内容可以伪装成任务的一部分，让模型把危险指令误判为目标要求。
- 模型有时能复述安全规则，但执行决策仍然可能偏离。

课程中提到一个对比：基于确定性规则的拦截比单纯依赖指令更稳。这个观点很适合文章使用：安全不能只交给“模型自觉”，需要在工具调用路径上加硬边界。

### 3. 五类威胁的共同根因

课程把 Agent 安全威胁拆成五类，但结论是这些风险最后都会落到工具调用。

| 威胁类型 | 课程中的含义 | 写作可用转译 |
| --- | --- | --- |
| 输入注入 | 不可信内容污染模型决策 | 任务、网页、文件、搜索结果都可能夹带恶意指令 |
| 权限越界 | Agent 做了原任务不应允许的事 | 不是“会不会做”，而是“有没有资格做” |
| 供应链风险 | Skill、工具、依赖本身带恶意逻辑 | Agent 的能力包也要进入安全边界 |
| 身份混淆 | 工具调用到底代表谁执行不清楚 | 没有身份边界，就无法做授权和审计 |
| 数据泄露 | 上下文、文件、凭据被带出系统 | 泄露通常发生在读数据与发请求之间 |

这五类威胁可以汇总成一句文章主线：Agent 被骗不可怕，可怕的是被骗以后仍然能顺利调用不该调用的工具。

## 三层工具能力限制

课程把工程方案分成三层：沙箱、权限网关、身份认证。它们不是替代关系，而是叠加关系。

### 第一层：沙箱与执行范围

沙箱解决的问题是：即使工具被调用，也要限制它能碰到什么。

课程中的实现方向包括：

- 限制文件路径，防止路径穿越。
- 检查危险命令和危险 shell 模式。
- 检查环境变量引用，避免把密钥从环境里带出去。
- 对输入做 URL decode，避免攻击者用编码绕过检查。
- 在工具执行前通过 Hook 统一检查。

这一层的写作重点：

- 沙箱不是只等于 Docker。
- Docker 隔离的是进程、文件系统和网络的一部分，但 Agent 还需要语义层面的工具参数检查。
- 对 Agent 来说，“能不能读这个路径”“能不能执行这个命令”“能不能访问这个域名”都要明确。

### 第二层：权限网关

权限网关解决的问题是：工具调用发生前，要有一个独立于模型的裁决器。

课程中的权限模型大致是：

- `allow`：直接允许。
- `ask`：需要人工确认。
- `deny`：直接拒绝。
- `default: ask`：默认不静默放行。
- `deny` 优先级最高。

这个设计非常适合放进文章，因为它能把“安全策略”变成很清楚的执行逻辑：

```text
Agent 想调用工具
        |
        v
权限网关读取策略
        |
        +-- deny  -> 拒绝并记录
        +-- ask   -> 暂停，交给人确认
        +-- allow -> 放行，进入真实工具
```

文章里可以强调：权限网关不是让模型再判断一次，而是把策略从上下文里拿出来，放进可测试、可审计的代码里。

### 第三层：身份认证

身份认证解决的问题是：工具到底以谁的身份执行。

课程里讨论了两种常见模式：

- 用户身份透传：Agent 调工具时继承用户身份。
- AI 服务账号：Agent 用独立的服务身份调用工具。

两种模式各有取舍：

| 模式 | 优点 | 风险/成本 |
| --- | --- | --- |
| 用户身份透传 | 权限更细，审计更接近真实用户 | 实现复杂，特别是 Shell、Skill、第三方工具链容易丢失身份 |
| AI 服务账号 | 接入简单，权限边界统一 | 粒度较粗，容易变成一个高权限共享身份 |

写文章时可以把这一节落到一个更实际的问题：当 Agent 删除文件、发邮件、查数据库时，审计日志里应该显示谁批准、谁执行、用的是什么权限。

## 代码实现映射

课程里的代码设计可以对应到本地 JS 版本文章里的几个角色：

| 课程角色 | 责任 | JS 文章可对应模块 |
| --- | --- | --- |
| `SandboxGuard` | 检查路径、命令、环境变量、shell 注入风险 | `toolGuard` / `sandboxGuard` |
| `PermissionGate` | 根据策略决定 allow / ask / deny | `permissionGateway` |
| `SecureToolWrapper` | 在真实执行前注入凭据，避免凭据暴露给模型 | `secureToolWrapper` |
| `AuditLog` | 记录工具、参数摘要、决策、原因、身份 | `auditLogger` |
| `security.yaml` | 声明式权限策略 | `security.config.js` 或 JSON 配置 |

注意这里文章要避免把 demo 写成“攻击证明”。更合适的写法是：用一个很小的 JS 例子展示工具调用链路在哪里被拦截，重点不是模拟一个真实攻击，而是把安全边界的位置讲清楚。

## 可直接用于文章的主线

可以把文章重构成下面这条线：

1. Agent 的危险不在“说错话”，而在“被任务骗了以后还能执行动作”。
2. Prompt 不是安全边界，因为它和不可信输入处在同一个上下文里。
3. 五类风险看起来不同，最后都会落到工具调用。
4. 所以真正要守的是工具调用入口。
5. 工具调用入口至少需要三道关：
   - 沙箱：限制执行范围。
   - 权限网关：决定 allow / ask / deny。
   - 身份认证：明确代表谁执行。
6. JS demo 应该服务于这条主线，只展示拦截链路，不要靠 mock 攻击撑故事。

## 文章里可以保留的表达

- “Agent 安全的关键，不是让模型永远不被骗，而是让它被骗以后也过不了工具调用这一关。”
- “Prompt 可以提醒模型，但不能替系统做授权。”
- “权限网关不是第二个模型裁判，而是一段可测试、可审计、可配置的确定性代码。”
- “沙箱限制能碰到哪里，权限网关限制能不能做，身份认证限制以谁的名义做。”
- “如果所有危险动作最后都要经过工具，那工具调用入口就是最值得防守的位置。”
