# Review 技术文章

## 概述

系统性 review 技术博客文章，覆盖六个维度，但**不要一次性列出全部问题**。先内部完成分析，再每次只提出一个最高优先级问题给用户决策。**不得在用户确认前擅自修改文件。**

Review 时要把 Ayou 2016-2025 年文章风格作为基准：**问题驱动、代码/源码作证、边做边讲、简短复盘**。不只检查文章是否"正确"，还要检查它是否像作者本人会写出来的文章。

## 工作流程

```
1. 读取文章文件
2. 按六个维度内部分析，形成问题队列
3. 只输出当前最高优先级的 1 个问题
4. 等待用户决策：修改 / 跳过 / 解释 / 停止
5. 根据决策处理后，再提出下一个问题
```

## 第一步：读取文章

用 Read 工具读取用户指定的文章文件。

## 第二步：按六个维度分析

必须在内部覆盖以下全部六个维度。分析时可以形成问题队列，但对用户输出时不要一次性展开所有维度和所有问题。

| 维度 | 检查重点 |
|---|---|
| **技术准确性** | 代码示例是否正确、概念是否有误、术语是否准确、数据/版本号是否会过时 |
| **表达清晰度** | 句子是否易读、专业术语是否有解释、示例是否直观 |
| **结构完整性** | 章节是否完整、逻辑是否循序渐进、是否缺少关键内容 |
| **语言风格** | 语气是否一致、是否符合目标读者、用词是否自然、配图风格是否与系列文章统一 |
| **逻辑合理性** | 论证是否有支撑、前后是否矛盾、结论是否过于武断 |
| **Ayou 风格匹配度** | 是否从具体问题/Demo/源码入口切入，是否代码和运行结果足够，是否保留个人学习痕迹，是否避免营销味和 AI 味 |

### Ayou 风格检查清单

逐篇检查这些信号：

- **开头**：是否用具体问题、疑点、题目、Demo、上篇遗留问题或"浅玩一下"切入；如果是空泛行业背景，标为问题。
- **证据**：关键结论是否有代码、源码路径、版本号、tag/PR、运行结果、截图或流程图支撑。
- **叙述方式**：是否是"边做边讲"，而不是先堆概念再给代码。源码文应顺入口函数往下扒；实现文应跟着能力增量走。
- **个人口吻**：是否自然保留"我们来试一试"、"接下来"、"简单分析下"、"个人认为"、"先 mark 一下"这类口吻。不要把所有口语都改掉。
- **篇幅和密度**：是否短段落、少铺垫、多代码/表格/示例。大段抽象解释要建议压缩。
- **系列连续性**：系列文章是否交代参考项目、代码仓库、本文 tag/PR、上篇做了什么、本篇补什么。
- **收尾**：总结是否只是回忆本文做了什么和下一步；如果出现升华、口号、泛泛展望，建议改短。

## 第三步：逐条提出问题

按优先级排序问题队列：高优先级在前；同优先级时，按技术准确性、逻辑合理性、结构完整性、Ayou 风格匹配度、表达清晰度、语言风格的顺序处理。

每次只输出一个问题，不要附带完整问题列表、优先级摘要或"后面还有 N 个问题"这种预告。除非用户明确要求总览，否则不要提前透露后续问题。

### 格式模板

```
## Review 问题 1

**[简短标题]**

- 维度：技术准确性
- 优先级：高

[说明问题所在，引用原文或代码]

建议修改：[具体修改方案]

---

你想怎么处理？回复：修改 / 跳过 / 解释 / 停止
```

### 输出规则

- 每次只输出 1 个问题。
- 问题编号按提出顺序递增，不按维度分别编号。
- 每个问题必须包含：标题、维度、优先级、问题说明、建议修改。
- 如果内部分析后没有发现问题，直接说"暂无明显问题"。
- 每次提出问题后必须停下来等用户决策，不得继续输出下一个问题。

## 第四步：等待用户决策

用户回复后的处理方式：

- **修改**：只修改当前这一个问题；修改完简要说明改了什么，然后继续提出下一个问题。
- **跳过**：不修改当前问题，继续提出下一个问题。
- **解释**：进一步解释当前问题和修改思路，不修改文件；解释后继续等待用户决策。
- **停止**：结束 review，不再提出后续问题。

如果所有问题都处理完，回复"Review 完成，暂时没有新的问题。"

## 常见错误

| 错误 | 修正 |
|---|---|
| 未覆盖全部六个维度 | 六个维度必须内部分析，但不要全部输出 |
| 一次性列出全部问题 | 每次只提出 1 个问题，等用户决策后再继续 |
| 输出优先级摘要 | 不输出总览摘要，直接提出当前最高优先级问题 |
| 没有明确邀请用户决策 | 最后一行必须让用户选择：修改 / 跳过 / 解释 / 停止 |
| 分析完直接修改文件 | 必须等用户对当前问题选择"修改"后才能修改 |
| 全篇只列问题不给建议 | 每个问题必须附上"建议修改"方案 |
| 把文章改得太官方 | 保留作者口语和学习过程，只修影响理解、可信度和风格一致性的问题 |
| 只查错不查风格 | 必须单独检查 Ayou 风格匹配度，指出是否缺少问题切入、代码证据、系列上下文或简短复盘 |
| 忽略配图风格一致性 | 同一系列文章的架构图/流程图应保持统一的配色、形状和排版风格（参考 `source/_posts/ai-agent-skill/flow.png` 的视觉基准：浅灰背景、蓝色圆角矩形、绿色胶囊入口、粉色菱形判断、橙色虚线旁注） |
| 连接线穿越框体 | 流程图/架构图的连接线不得穿越任何节点框体，必须沿框体外侧绕行；线上的标注文字不得覆盖任何框体 |
